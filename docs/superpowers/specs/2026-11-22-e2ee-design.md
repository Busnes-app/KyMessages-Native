# KyMessages-Native End-to-End Encryption Design

Date: 2026-11-22. Status: E1 and E2 merged; E3 built post-quantum (§3.1, §9.1) per the Ky PQC
Stack Plan (Busnes-app/ky-primitives#80 @ 5a8844c9, "KyMessages-Native E3 and E5"); E4–E6 not built.

Owner requirement (22 Nov 2026): **every room and every call is end-to-end encrypted.** The server
stores and relays ciphertext and keys it cannot open. This replaces the end-to-end encryption
KyMessages lost when Element was retired.

## 1. Owner decisions (fixed)

1. **Protocol: Olm + Megolm via vodozemac.** Pairwise Olm sessions between devices carry
   per-room Megolm sender keys. vodozemac (Rust, Apache-2.0, audited, `wasm_js` feature) is built
   into a small in-repo WebAssembly wrapper. We do not use `@matrix-org/matrix-sdk-crypto-wasm`
   (Matrix wire format) or `@matrix-org/olm` (deprecated libolm).
2. **Recovery: a recovery key only the user holds.** Clients upload a key backup that the
   recovery key encrypts. KyMessages stores ciphertext it cannot open. If the user loses the
   recovery key and every device, they lose their history.
3. **Bots become devices.** A bot is an end-to-end encrypted member with its own keys and reads
   only the rooms it is in. **Incoming room webhooks are removed**; integrations use a bot.
4. **Search runs on the device.** Each client indexes what it has decrypted. Server-side message
   search is removed. Push notifications carry no message text.
5. **Calls use frame encryption** (LiveKit E2EE / insertable streams) for P2P and SFU alike.
   The call key travels only over Olm.

## 2. What the server still sees

End-to-end encryption hides content, not metadata. The server sees, and this document and
`docs/PRODUCT.md` must say so:

- who is in which room, room names and topics, and who invited whom;
- when each message was sent, by which device, and its ciphertext size;
- reaction emoji and which message they react to (kept server-side so counts work);
- call start, end and participants; attachment sizes;
- device public keys, and which devices fetched which one-time keys.

## 3. Keys and identity

| Key | Holder | Purpose |
|---|---|---|
| Device identity (Curve25519 + Ed25519, a vodozemac `Account`) | One device | Olm sessions; signs the device's one-time keys |
| One-time keys and one fallback key (Curve25519) | Public on the server, private on the device | Start Olm sessions; each one-time key is claimed once, atomically |
| User master key (hybrid ML-DSA-65 + Ed25519, both must verify) | The user's verified devices; wrapped under the recovery key | Signs the user's devices, the backup key and (E4) bots; others pin its fingerprint |
| Key backup key (X-Wing, ML-KEM-768 + X25519) | Public on the server, signed by the master key; private half on verified devices and wrapped under the recovery key | Devices seal each Megolm session to it |
| Megolm outbound session | Sending device, per room | Encrypts that device's room messages |
| Call key (256-bit, random per call) | Call participants | LiveKit/P2P frame encryption |
| Recovery key (256-bit, random, symmetric only) | The user only | Wraps the master and backup private keys |

- **A device is trusted when the user's master key has signed it.** A client shares room keys
  only with devices that the member's pinned master key has signed. An unsigned device can send
  but receives no history and no keys until it is verified. This is the secure default: the
  server cannot add a device and read new messages.
- **Pinning others (TOFU):** the first master key seen for a colleague is pinned. A change is
  shown as a blocking warning in every shared room ("Bob's identity changed"), and keys stop
  flowing to Bob's devices until the viewer accepts the change.
- **Verifying a new device:** (a) a code (QR or copied text) shown by an already-verified device,
  relayed by its own one-time pairing (§3.1), or (b) the recovery key, which unwraps the master
  and backup keys. A user's first device creates the master, backup and recovery keys, shows the
  recovery key once and uploads nothing until the user confirms "I saved my recovery key".

### 3.1 Post-quantum identity (E3)

Olm and Megolm stay vodozemac's (Plan Q7: no custom crypto around them). Everything E3 adds is
post-quantum from the start, through one Go implementation that the server runs natively and the
browser runs as WebAssembly (Plan Q3): `internal/pqc/xwing` (HPKE base mode, KEM 0x647A X-Wing,
HKDF-SHA256, AES-256-GCM; public key 1216 B, wire `version 1 ‖ enc 1120 B ‖ ct`),
`internal/pqc/hybridsig` (ML-DSA-65 with an empty context and pure Ed25519, both over
SHA-256(domain ‖ 0x00 ‖ message), both required; kyguard's construction) and `internal/e2eeid`
(the KyMessages statements below), built by `web/pqc-wasm/build.sh` into the committed
`web/src/pqc/pqc.wasm`. `internal/e2eeid/testdata/vectors.json` pins both builds to the same bytes.
When ky-primitives ships `xwing` and `hybridsig`, the two `internal/pqc` packages become imports.

- **Statements.** Every signed or authenticated field list is length-prefixed (`Fields`: each
  field as a big-endian uint32 length and its bytes), so no two lists share bytes, and each use
  has its own label. The master key signs, under domain:
  - `kymessages.master.v1`: (alg, tenant, user, ML-DSA key, Ed25519 key), its self-binding;
  - `kymessages.device.v2`: (alg, tenant, user, device ID, curve25519, ed25519), a device;
  - `kymessages.backup-key.v1`: (alg, tenant, user, version, X-Wing public key), the backup key.
  `alg` is `mldsa65+ed25519`. Devices still self-sign `kymessages.device.v1` and
  `kymessages.otk.v1` with their vodozemac Ed25519 key (§9). The tenant is the org the key query
  names; a verified device refuses a query naming another org than its own identity's.
- **Fingerprint and TOFU.** The fingerprint is SHA-256(`kymessages.master-fingerprint.v1` ‖ 0x00
  ‖ Fields(alg, ML-DSA key, Ed25519 key)). The first master key seen for a colleague is pinned in
  the device's IndexedDB store; a mismatch is recorded and blocks room keys to every device of
  that user, with a warning in every shared room, until the viewer accepts the new fingerprint.
  A user's own key is pinned only by verification, never by first sight.
- **Synced pins.** Sign-out deletes the browser store, so pins also live on the server as one
  blob per user, AES-256-GCM under HKDF(master seed, `kymessages.pins.v1`) with AAD (label,
  tenant, user, counter): only the user's verified devices can read or replace it. Verification
  adopts the synced pins over first-sight pins made while unverified; later merges keep the most
  recently accepted pin per colleague. A server can withhold or roll back the blob (a fresh device
  then pins by first sight), but cannot forge it.
- **Recovery key.** 32 random bytes, never sent. Written as version 1 ‖ key ‖ 2-byte checksum in
  56 Crockford base32 characters, 14 groups of four. It wraps the master seed (64 B) and the
  backup seed (32 B) separately: AES-256-GCM under HKDF-SHA256(key, label) with labels
  `kymessages.recovery.v1/master-key` and `kymessages.recovery.v1/backup-key`, AAD (version
  label, purpose label, tenant, user). A restoring device requires the unwrapped seeds to derive
  exactly the published master and backup keys and their signatures to verify.
- **Key backup.** Each Megolm inbound session (export at its first known index, with its sender
  binding) is sealed with `xwing.Seal` to the published, master-verified backup key, info
  `kymessages.backup.v1`, AAD Fields(room ID, session ID). Anyone with the public key, the server
  included, can seal to it, so the plaintext also carries an HMAC under HKDF(master seed,
  `kymessages.backup.v1/mac`); a restore drops entries without it. Restored sessions are marked
  `from_backup`.
- **QR verification.** A verified device opens a pairing (3 minutes, one per user, consumed once)
  and shows version 1 ‖ pairing ID (16 B) ‖ one-time secret `s` (32 B) ‖ master fingerprint (32 B),
  base64url, never a public key. The new device checks that the server's master key has that
  fingerprint and posts an ephemeral X-Wing public key. Both screens show six digits,
  HMAC(`s`, label ‖ pairing ID ‖ ephemeral key), so the server cannot grind a substitute key; on a
  match the verified device sends AES-256-GCM under HKDF(`s`, `kymessages.qr-transfer.v1`) of the
  master and backup seeds, `xwing.Seal`ed to the ephemeral key with info
  `kymessages.qr-transfer.v1`; both layers bind (label, pairing ID, verified device, new device).
  `s` never reaches the server, so the transfer stays confidential even if X-Wing breaks, and the
  X-Wing layer protects against a photographed QR plus recorded server traffic. The new device
  checks the seeds derive the published keys before it signs itself.
- **Residual (Plan, stated plainly).** Room keys still travel between devices over Olm, which is
  classical: recorded to-device ciphertext (mailbox rows and their backups) is
  harvest-now-decrypt-later exposed until vodozemac ships a PQ Olm (PQXDH PR #120, on hold). Mail
  is deleted on acknowledgement and kept at most 30 days to keep that window short.

## 4. Rooms and messages

- **All rooms are encrypted**, with no per-room switch. Existing rooms become encrypted on
  upgrade.
- **Envelope** (`encoding: "e2ee_room_v1"`, already reserved in `store.MessageEncodingE2EERoomV1`):
  `{"alg":"megolm.v1","sender_key","device_id","session_id","ciphertext"}`. The plaintext inside
  carries `room_id`, `type` (`text`, `edit`, `reply`, `attachment`) and the content, so a
  ciphertext replayed into another room fails to decrypt-check.
- **Key sharing:** before the first message, the sender creates a Megolm session and sends its
  key over Olm to every trusted device of every current member. Messages go out as to-device
  messages, relayed through a server mailbox (`e2ee_to_device`, per recipient device, deleted on
  ack, kept 30 days).
- **Rotation:** a device starts a new Megolm session when a member leaves or is removed, when a
  member's device is removed, after 100 messages, or after 7 days. Joiners get the current
  session from its ratchet index onward only, so they never see history from before they joined.
- **System events** (`system_v1`: joins, leaves, renames) stay server-authored plaintext metadata.
- **Legacy history:** messages stored before the upgrade stay `plain_v1`, are shown with a
  "Sent before encryption" label, and are never re-encrypted. A fresh-database operator
  command, `kymessages purge-plaintext`, deletes them.
- **Edits and deletes:** an edit is a new encrypted message pointing at the original. A delete
  removes the ciphertext server-side, as today.

## 5. Attachments

Format discipline (Plan, E5): a separate random AES-256-GCM key for each file and each
thumbnail; metadata carries `v` and `alg` (`A256GCM`); AAD `kymessages.attachment.v1` ‖ kind
(`file`, `thumb`); the SHA-256 of the ciphertext rides inside the encrypted message. Choose a
chunked (STREAM) format at the start if files can exceed one in-memory AES-GCM call.

The client encrypts each file with AES-256-GCM under a random key before upload. The key, nonce
and SHA-256 of the ciphertext go inside the encrypted message. The server stores and serves only
ciphertext, and quota checks use ciphertext size. Thumbnails are made and encrypted on the
client. Existing attachments stay as they are, under the legacy label.

## 6. Search, notifications and suite features

- **Search:** each client keeps an IndexedDB index of decrypted text, encrypted at rest under a
  non-extractable WebCrypto key. `GET /api/v1/search` and the FTS/`tsvector` index are removed.
- **Push:** the payload says only "New message" and names the room (the room name is already
  server metadata). `push_handlers.go` already strips `e2ee_room_v1` previews.
- **Suite routes are unaffected:** `/api/suite/chat` returns a DM link, presence reads
  KyCalendar/KyPost inputs, and KyCalendar meeting rooms are created server-side with no
  messages. None of them read content.

## 7. Calls

- **Frame encryption everywhere.** LiveKit's E2EE (`ExternalE2EEKeyProvider`, insertable streams
  or `RTCRtpScriptTransform`) encrypts media frames under the call key, for SFU calls and for
  P2P calls. P2P needs it too: DTLS-SRTP fingerprints travel through the server's signaling, so a
  malicious server could otherwise sit in the middle. A browser without encoded-transform
  support cannot join a call; it is told so and offered nothing weaker.
- **Call key:** the first joiner mints it and sends it over Olm to each participant device as
  it joins, using the existing `e2ee_key` signal slot (`internal/chat/protocol.go`). The key
  rotates when a participant leaves.
- **Guests (`/meet/{token}`):** guests are not members and have no Olm identity. A guest's
  browser makes an ephemeral **X-Wing** key pair (never classical X25519; Plan row 22) and sends
  the public key with its knock. The member who admits the guest seals the call key to it with
  `xwing.Seal` (the shared `internal/pqc/xwing` build). Both screens show a 4-word
  code derived from the guest key, so the admitter can compare it with the guest out of band.
  Keys are never put in guest URLs, because the server mints those links
  (`PUT /api/meetings/{id}`).

## 8. Bots

- A bot (`kybot_` token) registers a device and a master key like a user. The owner's client signs
  the bot's master key at creation, and colleagues see "Bot, verified by <owner>".
- The agent skill bundle (`agent-skill/`) ships the vodozemac Python bindings, so OpenClaw/Hermes
  bots decrypt and encrypt locally. A bot's keys live with the bot, never on the server.
- **Incoming webhooks are removed.** Migration disables every existing webhook and writes an
  audit row. `POST /api/v1/webhooks/in/{id}` answers `410 gone` with a pointer to bots. The admin
  UI drops the webhooks pane.

## 9. Server changes

| Area | Change |
|---|---|
| Store | `e2ee_devices` (tenant, user, device_id, identity keys, master-key signature and version), `e2ee_one_time_keys` (claim-once), `e2ee_to_device` mailbox, `e2ee_master_keys` (migration 68: public keys, signatures, recovery wraps, sealed pins, version), `e2ee_key_backup` (sealed sessions per identity version), `e2ee_pairings` |
| API | `POST /api/v1/keys/upload`, `/keys/query` (with `tenant_id` and `master_keys`), `/keys/claim`, `PUT /api/v1/to-device`, `GET` + ack, `GET/PUT /api/v1/keys/master`, `PUT /api/v1/keys/pins`, `POST /api/v1/keys/devices/{id}/signature`, `GET/PUT/DELETE /api/v1/keys/backup`, `/api/v1/keys/pairings` (§9.1) |
| Messages | Accept only `e2ee_room_v1`; `plain_v1` stays allowed for `kybot_` tokens only until E4 (§10) |
| Removed | Server search, incoming webhooks |
| Tenancy | Every key table is tenant-scoped; key queries and claims never cross an org |
| Backups | Capsules carry ciphertext, public keys and the encrypted key backup; restore keeps them |
| Revocation | Removing a device deletes its keys and to-device mail; clients then rotate |

**Signed strings.** Keys and signatures are unpadded base64, as vodozemac writes them. A device
signs, with its Ed25519 key:
- its identity: `kymessages.device.v1\n<user_id>\n<device_id>\n<curve25519>\n<ed25519>`;
- each one-time and fallback key: `kymessages.otk.v1\n<user_id>\n<device_id>\n<key_id>\n<key>`.

The server checks both and refuses anything else in an upload, to reject garbage early. Clients
check again, because they cannot trust the server. A device's identity keys never change:
re-uploading other keys answers `409`. A new mailbox message sends a `to_device` WebSocket event to
the recipient user.

### 9.1 E3 routes

- `GET /api/v1/keys/master` answers `{tenant_id, master}`: null, or `{version, master_key,
  self_signature, backup_key:{public_key, signature}, recovery:{wrapped_master_key,
  wrapped_backup_key}, pins:{counter, sealed}}`. `PUT` takes `{expected_version, master_key,
  self_signature, backup_key, recovery}`, verifies both hybrid signatures for the caller's org and
  user and version `expected_version + 1`, and answers `409` unless `expected_version` is current
  (0: none). A replacement (reset) needs a sign-in from the last 10 minutes (the console's
  step-up, `reauthentication_required`) and deletes the key backup, pins, pairings and every device
  cross-signature in the same transaction; colleagues then see the identity change. Audited
  `e2ee.master_key_set` / `e2ee.master_key_reset`.
- `POST /api/v1/keys/devices/{id}/signature {version, signature}` stores a verified
  cross-signature on one of the caller's devices (`409` for a stale version). `/keys/query` lists
  only cross-signatures by the current version.
- `PUT /api/v1/keys/pins {version, expected_counter, sealed}`: compare-and-swap.
- `PUT /api/v1/keys/backup {version, sessions:[{room_id, session_id, first_index, sealed}]}` (1–100;
  a session keeps the copy with the lowest first index; at most 20,000 per user, `507` past it);
  `GET ?version=&after_room=&after_session=` pages 200 at a time; `DELETE ?version=` empties it.
- Pairings: `POST /api/v1/keys/pairings {device_id}` (only a device cross-signed by the current
  key; cancels the user's other pairings) answers `{pairing_id, expires_at}`; `GET …/{id}` answers
  its state, never the sealed keys; `POST …/{id}/join {device_id, ephemeral_key}` once;
  `PUT …/{id}/sealed {device_id, sealed}` once, from the initiator; `POST …/{id}/consume
  {device_id}` hands the sealed keys to the joined device and deletes the row in one statement;
  `DELETE …/{id}` cancels. Another user's or org's pairing reads as unknown; expired rows are
  unreadable at once and swept every minute; a restore deletes them.
- Every E3 body is decoded strictly and none has a field for a private key, recovery key, seed or
  session key (`TestE2EEIdentityBodiesCarryNoSecrets`, `TestE2EEIdentityRoutesRefuseSecretFields`).
  Capsules carry `e2ee_master_keys` and `e2ee_key_backup` (the whole database) and restore keeps them.

The server never receives a private key, a Megolm session key, a call key or a recovery key.
Tests assert this, for example that no request body the server accepts can carry a field
named like a private key.

## 10. Build plan

Every phase leaves every feature working: no phase refuses a message, a bot, a webhook or a
search that the previous phase allowed without shipping its replacement in the same PR. Images
publish only from a published GitHub release (`release-image.yml`), not from a merge to `main`,
so `main` can carry finished phases ahead of the release that switches encryption on.

1. **E1: crypto core and key server** (PR #26). The `web/crypto` Rust crate (vodozemac +
   wasm-bindgen), with its committed `.wasm` reproduced in CI (as `web/dist` is), the key and
   to-device tables, and the key API with tests, including that one-time keys are claimed
   exactly once across replicas. It changes no existing behaviour.
2. **E2: encrypted rooms.** Megolm send and receive, key sharing and rotation, and the IndexedDB
   store. The web client sends only `e2ee_room_v1`. Bots and webhooks keep working, labelled. In
   the same PR, so nothing is left half-working:
   - **Search moves to the device.** The on-device index replaces `GET /api/v1/search`, which is
     removed; the FTS/`tsvector` index skips `e2ee_room_v1` rows, so it never indexes ciphertext.
   - **Incoming webhooks are removed** (§8): disabled by migration with an audit row,
     `410 gone`, and the pane dropped. Their supported path, bots, still works through E2–E4.
   - **Push previews go.** Notifications say only "New message".
   - **Transition:** the server still accepts `plain_v1`, but only from `kybot_` tokens. The UI
     shows those messages as "Not encrypted (bot)". Every other client is refused `plain_v1`.
3. **E3: identity and recovery** (built post-quantum, §3.1, §9.1). The master key, device
   signing, TOFU warnings, QR verification, the recovery key and key backup. Room keys go only to
   devices the pinned master key signed.
4. **E4: bots as devices.** Bot devices, the Python vodozemac bundle in `agent-skill/`, and the
   owner signing the bot at creation. This PR also makes the server refuse `plain_v1` from
   everyone, bots included, so it ends the E2 transition.
5. **E5: attachments.** Client-side file encryption. **Transition E2–E4:** files uploaded
   before E5 stay plaintext on the server and show a "File not encrypted" label inside the
   encrypted message.
6. **E6: calls.** Frame encryption for P2P and SFU, call key distribution and rotation, and the
   guest admission key with its 4-word code. **Transition until E6:** calls keep today's
   DTLS-SRTP (encrypted in transit, readable by the SFU), and the call screen says so.

**Release gates.**
- **First encryption release:** E1–E5. Encrypted rooms without identity verification (E3) would
  trust whatever devices the server lists, and bots (E4) and files (E5) must not be left
  plaintext. No GitHub release is published from `main` while E2 is merged and E3–E5 are not.
- **Copy for that release:** "messages and files are end-to-end encrypted; calls are not yet."
- **Calls:** E6 ships in a later release. Only then does the copy add calls.

## 11. Claims and review

- Product copy says "end-to-end encrypted (not independently audited)" until an outside review.
  Section 2's metadata list ships alongside it in `docs/PRODUCT.md`.
- A hostile review of E1–E5 runs before release, focused on these: whether the server can add a
  device, whether old keys reach new members, replay across rooms, and one-time key exhaustion.
