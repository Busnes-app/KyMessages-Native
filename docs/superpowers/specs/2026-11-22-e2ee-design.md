# KyMessages-Native End-to-End Encryption Design

Date: 2026-11-22. Status: E1 and E2 merged; E3 built post-quantum (§3.1, §9.1) per the Ky PQC
Stack Plan (Busnes-app/ky-primitives#80 @ 5a8844c9, "KyMessages-Native E3 and E5"); E4–E6 not built.

Owner requirement (22 Nov 2026): **every room and every call is end-to-end encrypted.** The server
stores and relays ciphertext and keys it cannot open. This replaces the end-to-end encryption
KyMessages lost when Element was retired.

## 1. Owner decisions (fixed)

1. **Protocol: Olm + Megolm via vodozemac.** Pairwise Olm sessions between devices carry
   per-room Megolm sender keys. vodozemac (Rust, Apache-2.0, audited, `wasm_js` feature) is built
   into a small in-repo WebAssembly wrapper. We do not use `@matrix-org/matrix-sdk-crypto-wasm`
   (Matrix wire format) or `@matrix-org/olm` (deprecated libolm).
2. **Recovery: a recovery key only the user holds.** Clients upload a key backup that the
   recovery key encrypts. KyMessages stores ciphertext it cannot open. If the user loses the
   recovery key and every device, they lose their history.
3. **Bots become devices.** A bot is an end-to-end encrypted member with its own keys and reads
   only the rooms it is in. **Incoming room webhooks are removed**; integrations use a bot.
4. **Search runs on the device.** Each client indexes what it has decrypted. Server-side message
   search is removed. Push notifications carry no message text.
5. **Calls use frame encryption** (LiveKit E2EE / insertable streams) for P2P and SFU alike.
   The call key travels only over Olm.

## 2. What the server still sees

End-to-end encryption hides content, not metadata. The server sees, and this document and
`docs/PRODUCT.md` must say so:

- who is in which room, room names and topics, and who invited whom;
- when each message was sent, by which device, and its ciphertext size;
- reaction emoji and which message they react to (kept server-side so counts work);
- call start, end and participants; attachment sizes;
- device public keys, and which devices fetched which one-time keys.

## 3. Keys and identity

| Key | Holder | Purpose |
|---|---|---|
| Device identity (Curve25519 + Ed25519, a vodozemac `Account`) | One device | Olm sessions; signs the device's one-time keys |
| One-time keys and one fallback key (Curve25519) | Public on the server, private on the device | Start Olm sessions; each one-time key is claimed once, atomically |
| User master key (hybrid ML-DSA-65 + Ed25519, both must verify) | The user's verified devices; wrapped under the recovery key | Signs the user's devices, the backup key and (E4) bots; others pin its fingerprint |
| Key backup key (X-Wing, ML-KEM-768 + X25519) | Public on the server, signed by the master key; private half on verified devices and wrapped under the recovery key | Devices seal each Megolm session to it |
| Megolm outbound session | Sending device, per room | Encrypts that device's room messages |
| Call key (256-bit, random per call) | Call participants | LiveKit/P2P frame encryption |
| Recovery key (256-bit, random, symmetric only) | The user only | Wraps the master and backup private keys |

- **A device is trusted when the user's master key has signed it and lists it.** A client shares
  room keys only with devices that the member's pinned master key cross-signed and names on its
  newest signed device list. A device that is not yet verified can post, but receives no keys and
  trusts no one, so it shares its own room keys with no one either until it is verified. This is
  the secure default: the server cannot add a device, or bring a removed one back, and read new
  messages.
- **Pinning others (TOFU):** the first master key seen for a colleague is pinned. A change is
  shown as a blocking warning in every shared room ("Bob's identity changed"), and keys stop
  flowing to Bob's devices until the viewer accepts the change.
- **Verifying a new device:** (a) a code (QR or copied text) shown by an already-verified device,
  relayed by its own one-time pairing (§3.1), or (b) the recovery key, which unwraps the master
  and backup keys. A user's first device creates the master, backup and recovery keys, shows the
  recovery key once and uploads nothing until the user confirms "I saved my recovery key".

### 3.1 Post-quantum identity (E3)

Olm and Megolm stay vodozemac's (Plan Q7: no custom crypto around them). Everything E3 adds is
post-quantum from the start, through one Go implementation that the server runs natively and the
browser runs as WebAssembly (Plan Q3): `github.com/Busnes-app/ky-primitives/xwing` (HPKE base mode, KEM 0x647A X-Wing,
HKDF-SHA256, AES-256-GCM; public key 1216 B, wire `version 1 ‖ enc 1120 B ‖ ct`, info starting
with a caller label), `github.com/Busnes-app/ky-primitives/hybridsig` (ML-DSA-65 with an empty context and pure Ed25519,
both over SHA-256(label ‖ 0x00 ‖ message), both required; kyguard's construction; keys and
signatures encoded `"mldsa65+ed25519" 0x00 ‖ ML-DSA-65 half ‖ Ed25519 half`) and
`internal/e2eeid` (the KyMessages statements below). `scripts/build-pqwasm.sh` builds the pinned
ky-primitives v0.11.0 `cmd/pqwasm` sources with `internal/e2eeid/pqwasm/identity.go`, the product's
wire adapter, into the ignored `web/src/pqc/pqc.wasm`; no primitive source or compiled WASM is
vendored. npm builds/tests generate both crypto cores before use.
`internal/e2eeid/testdata/vectors.json` pins the native and
WebAssembly builds to the same bytes. On the wire, master keys and signatures are unpadded base64
of the tagged encodings.

- **Statements.** Every signed or authenticated field list is length-prefixed (`Fields`: each
  field as a big-endian uint32 length and its bytes), so no two lists share bytes, and each use
  has its own label. The master key signs, under domain:
  - `kymessages.master.v1`: (alg, tenant, user, tagged public key), its self-binding;
  - `kymessages.device.v2`: (alg, tenant, user, device ID, curve25519, ed25519), a device;
  - `kymessages.backup-key.v1`: (alg, tenant, user, version, X-Wing public key), the backup key;
  - `kymessages.device-list.v1`: (alg, tenant, user, version, epoch, device IDs sorted and
    distinct), the user's devices. A device adds itself when it is verified and removes itself at
    sign-out (and abandoned devices once a verified device can sign);
  - `kymessages.device-list-reserve.v1`: (alg, tenant, user, version, expected epoch, digest of
    the proposed list), a reservation of the next list epoch: its own domain, so a reservation
    never verifies as a list nor a list as a reservation;
  - `kymessages.pins-write.v1`: (alg, tenant, user, version, new counter, SHA-256 of the sealed
    set), each pin set write;
  - `kymessages.backup-write.v1`: (alg, tenant, user, version, backup generation, entry count,
    then per entry Fields(room, sender key, session, first index) and the SHA-256 of its sealed
    bytes), each key backup write. The server checks these two, the device list and cross-signatures against
    the master key of the version named, read and locked in the write's own transaction.
- **Device list authority.** Every device keeps a high-water mark per (tenant, user, master
  fingerprint, version): the newest epoch seen and a digest of its members, raised atomically in
  one storage transaction so a status check and an unlocked sign-out cannot lower it. Readers
  and writers refuse a list that is older (a rollback), different at the same epoch (a fork), or
  missing once one was seen; a missing list is a start only with no history. A list no newer than
  the mark is checked without a storage write. Before signing a change, a device requires the
  current list to be canonical and signed by its own master key for exactly that org, user and
  version. It then reserves the next epoch for exactly the proposed list (its digest,
  SHA-256 of Fields(`kymessages.device-list`, IDs…)) for 30 seconds, with the master key's
  reservation signature, which the server checks against the master row it locks for the
  reservation: a session without the master seed cannot hold the list. The server answers the
  epoch to sign and how long the reservation holds, and the device signs only once it holds it,
  never under one it knows has lapsed. Of two devices editing at once, the second is refused
  before it signs (told when the holder's reservation lapses), looks again every second until
  the holder's edit lands or the lease ends (it waits past the 30-second lease, so an abandoned
  reservation never fails an edit early), and applies its change to the winner, so a losing
  proposal is never a signed successor anyone can be shown. The server publishes a list only
  under a live reservation of its digest and epoch; reserving the same digest again keeps its
  epoch (an honest retry), and a different proposal replacing a lapsed reservation gets a higher
  epoch, so two proposals are never signable at one epoch (epochs may skip). Only a list the
  server took is recorded as seen. The lease is counted from before the request on the
  monotonic clock, so a grant that arrives late is not signed under once spent; the server
  judges it again by its clock read after it holds the row lock. Waiting out another device's
  reservation never happens under the per-user lock: a status check gives up at once and leaves
  the listing to the bounded retry, which waits unlocked. Other conflicts retry four times with
  backoff, then say so.
  A fork, once seen, stays a fork for that epoch whichever list the server shows next, until a
  validly signed list at a higher epoch. A rolled-back or forked own list or pin set is reported in the identity status,
  never signed over: re-signing an old roster or an empty pin set to get past the mark would
  bring back what the newer state removed. The device then offers an identity reset (step-up),
  which keeps this device's room keys and history; everyone the user shares rooms with sees an
  identity change to accept.
  Sign-out removes the device from the list (bounded, without the per-user lock); if that does
  not become durable, the retirement stays pending in the browser (outliving the wiped crypto
  store) until a verified device signs it, and deleting the server row alone never completes it.
  A retiring device is never added back by its own status check, nor by an enrollment already in
  flight when sign-out started: an enrollment checks for that right before it reserves, and a
  removal publishes even when the device is already absent, so its reservation is ordered after
  any enrollment holding the list and it confirms only once that enrollment landed (and is then
  removed) or lapsed. Each pending retirement is its own browser entry,
  so tabs recording different devices never overwrite each other; an entry goes only once both
  the signed removal and the row deletion are confirmed (by any tab, however late), and pending
  ones run again as soon as a device has durably taken on the identity by QR or recovery,
  before its backup is read. A sign-out the server refuses after retirement touched the device
  replaces it with a new device, which lists itself, once the bounded attempt ends, even if the
  deletion never answers; the old one stays pending. A refused sign-out whose attempt had not
  yet reached a device (a slow start-up) is fenced, so it never touches the device that start-up
  later yields; only the device a retirement actually touched is replaced. Replacing deletes
  that device's own keys only (`device`, `account`, `fallback`, `olm:`, `out:`): the identity
  seeds, room keys, replay log, pins and backup queue stay, so the new device is verified
  without the recovery key. A stored device found pending at start is replaced before it runs,
  so the device in use is never the one being deleted. A refused sign-out fences an attempt
  that has not touched a device at once, before waiting on one that has, and an attempt checks
  that its device is still the one in use right before touching it. A confirmation that arrives after its
  device was settled (by any tab) never brings the record back, and a clean sign-out's wipe
  does not record a device this tab saw fully retired. **Limits:** a device with no history (a fresh browser) accepts the
  list it is first shown; every verified device holds the master seed, so removing a device from
  the list stops others trusting it but cannot stop a device that kept the seed from signing as
  the user: losing a device that held it calls for an identity reset. The reservation is the
  server's word, not cryptography: an equivocating server can grant two devices the same epoch
  and so produce a fork, which a reader detects only when it sees both lists (and then trusts
  no device of that user); a withholding server can stall list edits or serve one device an old
  view. Nothing here proves the server committed one shared state.
  `alg` is `mldsa65+ed25519`. Devices still self-sign `kymessages.device.v1` and
  `kymessages.otk.v1` with their vodozemac Ed25519 key (§9). The tenant is the org the key query
  names; a verified device refuses a query naming another org than its own identity's.
- **Fingerprint and TOFU.** The fingerprint is SHA-256(`kymessages.master-fingerprint.v1` ‖ 0x00
  ‖ tagged public key). Only a verified device pins. A first sight is only a proposal: every
  first sight of one trust check is committed to the synced pin set in one compare-and-swap
  before any of those members' devices gets a key, and stored locally only once the server took
  it. On a conflict the device refetches and evaluates the winner: a different key another of
  the user's devices pinned first stands, and this device's key becomes a pending change. A
  failed commit shares nothing and pins nothing. A mismatch is recorded as a pending change,
  which is checked before the pin, so a server going back to the old key cannot lift it; a newer
  verified key replaces the candidate shown (still untrusted). It blocks room keys to every
  device of that user, with a warning in every shared room (room open runs the check too, so
  readers see it), until the viewer accepts exactly the change shown (old and new fingerprint;
  a click acts only on what was shown: if the shared pin already is the clicked key but this
  device's pending candidate moved on to another key, the shared record is adopted, the newer
  candidate stays, rebased onto it, and the click is refused;
  the full fingerprint is displayed). Accepting syncs the pin set first and, on every
  compare-and-swap attempt, requires the pending change to be exactly that, this device's pin
  the old fingerprint and the shared pin present and the old fingerprint; the pin changes on the
  device only once the signed shared write took it, so a prompt made stale by another device's
  accept is refused and redrawn. A shared pin that is already the new key (another device
  accepted it, perhaps over several hops) is adopted as it is, predecessor included. A missing
  shared pin accepts nothing; that attempt still writes the synced set, so the next accept
  meets a confirmed baseline. A user's own key is pinned only by verification, never by first sight.
- **Synced pins.** Sign-out deletes the browser store, so pins also live on the server as one
  blob per user, AES-256-GCM under HKDF(master seed, `kymessages.pins.v1`) with AAD (label,
  tenant, user, counter): only the user's verified devices can read or replace it. Each pin
  records a change count, whether it was accepted, and the fingerprint an accepted change
  replaced; a device adopts another device's different pin only as an accepted change from
  exactly its own pin; any other disagreement (including a change more than one hop from its
  pin) leaves the synced pin as it is and keeps this device's pin and a pending change, which the
  user resolves by accepting exactly what is shown. When another device's accepted change moves
  the pin, a pending change here for yet another key is rewritten to change from the new pin. A verified device syncs once before every
  trust check (sends, room opens and mailbox reads alike), and a failed sync fails the check
  rather than deciding trust; first sights happen only after an authenticated sync. The counter's
  high-water mark is scoped to (tenant, fingerprint, version), so a reset's new identity starts
  at 0 and a rollback of it is still refused. A set that does not open is an error, never an
  empty set. Writes carry the master key's `kymessages.pins-write.v1` signature. A server can
  withhold the blob, but not forge or roll it back.
- **Local seeds.** The master and backup seeds are stored AES-GCM-wrapped under a key derived
  from the store's pickle key. No server answer deletes them: an identity the server no longer
  lists (a bumped version, a restore, none at all) is set aside under `identity:previous:*` and
  taken back if the server lists it again.
- **Room key precedence.** A room session's primary copy authenticates what it covers when it
  came over Olm from a vouched device. Such a copy is never replaced by one that does not; an
  earlier reach from an unvouched copy is kept beside it as the cover (`inb:`), for older
  messages only, and unauthenticated. A vouched copy supersedes an unvouched or restored primary
  from its own index on (at an equal index too), and the old one becomes the cover for what only
  it reaches. Only copies that authenticate are queued for the key backup. A restore lets a
  valid backup copy reach over an unvouched one, still unauthenticated (`restored`).
- **Sending.** An unverified device trusts no one, so an encrypted message from it would reach no
  one: the engine refuses the send before any session is made or ratcheted, with a reason that
  points to the identity gate's setup or verification, and the message's Retry sends it once
  the device is verified. Holding the seeds is not enough: from the send's own key query, the
  device must be cross-signed by the identity the server publishes now and on its newest signed
  list, with exactly this device's own keys (other validly signed keys listed under its ID are
  not this device), so a replacement still enrolling, a removed device, or seeds of an identity
  reset elsewhere are refused the same way. A refused send pins no one: the change warnings and
  list observations it made are kept, its first sights are not committed. A rolled-back pin set
  found while checking a send or a mailbox's senders is the verdict the gate shows, and the mail
  stays queued. A verified device alone in a room sends to itself as before.
- **Recovery key.** 32 random bytes, never sent. Written as version 1 ‖ key ‖ 2-byte checksum in
  56 Crockford base32 characters, 14 groups of four. It wraps the master seed (64 B) and the
  backup seed (32 B) separately: AES-256-GCM under HKDF-SHA256(key, label) with labels
  `kymessages.recovery.v1/master-key` and `kymessages.recovery.v1/backup-key`, AAD (version
  label, purpose label, tenant, user). A restoring device requires the unwrapped seeds to derive
  exactly the published master and backup keys and their signatures to verify.
- **Key backup.** Each Megolm inbound session that arrived from a device its member's master key
  vouches for (export at its first known index, with its sender binding) is sealed with
  `xwing.Seal` to the published, master-verified backup key, info `kymessages.backup.v1`, AAD
  Fields(room ID, sender curve25519 key, session ID, first index). Sessions from unvouched
  devices never enter the backup, so no one can fill it or bake an impersonation into it.
  Anyone with the public key, the server included, can seal to it, so the plaintext also carries
  an HMAC under HKDF(master seed, `kymessages.backup.v1/mac`) over the same fields and the export;
  a restore drops entries without it. Messages read through a restored session, or from an
  unvouched sender, are marked unauthenticated, and the message row says which. A session this
  device holds verified keeps that record; a backup copy reaching earlier is kept beside it and
  read only for older messages, as unauthenticated (and a vouched Olm copy takes over from a
  restored one the same way). Writes carry the master key's `kymessages.backup-write.v1`
  signature, so only a device holding the master seed can add to the backup. The server keys
  rows by (room, sender key, session), keeps the lowest first index (bytewise order on both
  engines: `COLLATE "C"` on PostgreSQL), and caps a user at 2,000 sessions and 2 MiB of sealed
  text (4 KiB an entry): the whole database is one capsule member, capped at 64 MiB. An entry
  that would pass a cap, a better copy of a stored session included when its bytes do not fit,
  is refused and named in the reply; the rest of the batch lands. Refused entries stay queued on
  the device (retried on each status check, not on every new key), and the backup shows as full
  while any wait. A new identity, or a deletion seen from another device, queues them again.
  Deleting the backup bumps its generation, which every write is signed for, so a write signed
  before the deletion cannot refill it; a device learns the new generation from the refusal.
  **Open decision:** this bounds backed-up history to about 1,000 sessions a user; keeping more
  needs the backup outside the capsule database.
- **Restore.** A restore pages the backup in (at most 200 entries a page and 2,000 in all), each
  page under its own lock, requires the cursor to move strictly forward, and stores it after each
  page, so a reload or the next status check resumes it; each page's sessions reopen waiting
  messages as they arrive. Queued sessions drain on start and on every status check.
- **Availability is not a verdict.** A post-quantum module that is not running (not yet loaded,
  crashed, exited) is `PQCUnavailable`, like a network or storage failure: the backup queue, the
  restore cursor and to-device mail are kept for a retry, no signature reads as invalid, and no
  room key is stored as unvouched because the sender lookup failed. The module reloads; one start
  (fetch, compile and the Go program's hand-over) is bounded by 10 seconds. Each start passes
  its generation to the Go program, which hands it back with its call, so a start given up on
  cannot install itself through the newest start's handler; a start that could not fetch,
  compile or run the module, or ran out of time, is `PQCUnavailable` too. At the key server
  boundary an unreachable server, `429` and `5xx` are unavailability; other refusals stay
  verdicts and an abort stays an abort. At the storage boundary every failed or aborted
  IndexedDB request or transaction is `StorageUnavailable`. A mailbox drain that hits one
  acknowledges only the mail handled before it, announces the keys already stored, keeps the
  rest queued and still fails, so its retry comes. Work that failed
  for availability (the mailbox, the backup, a restore) is retried on a bounded schedule (2 s to
  60 s, five times). A retry awaits that work itself (the mailbox, signing this device if that
  failed, an unlocked listing of it, the restore in progress, the backup queue with refused
  entries), one at a time, and only its end resets the schedule and clears the pending notice;
  a failure reported while it runs earns one more pass, even when the pass then ends in a
  verdict. A rollback found while listing is reported, and the restore and backup still run. A
  failure reported before anyone listened (a replaced device signing itself at start) is handed
  to the first listener. A pass that ends in a verdict (a rollback or fork) refreshes the
  identity gate, which then offers the reset. The chat page's readiness follows the user's
  device through retries and replacements; once it runs, the start-up error goes, and only that
  error. Identity status checks belong to the device start-up they were asked of (one running,
  one shared next of that same start-up): one asked of a start-up since replaced, reset under it
  or ended never runs on, nor waits for, the current one, never starts a device, and its answer
  is dropped; a start-up's own failure is still its answer. Only a fresh check starts the user's
  device again. Identity notices, and the completion of a setup, restore or QR verification,
  reach the page only from the start-up in use. While a device is being reset no start-up
  begins in any tab: the resetting tab tells the others before it waits on their lock and again
  once the reset is stored (or failed); they start nothing until then (or a bounded wait), and
  then the gate asks again. A replacement announces itself. The budget belongs to the signed-in user's session: a start-up that
  fails again does not refill it, and nothing from an ended session (a sign-out, another user)
  schedules or changes the next. Once the schedule is spent the notice says retries stopped,
  and Retry now runs it again; a device that could not start shows the same notice. A change in
  what the backup refuses updates the notice after every stored batch, even while a later one
  stalls or fails, without a status check. A session queued afresh while its refused entry
  waits is uploaded once. (Refused entries are still re-sent on every status check; capping
  that is left as a follow-up.) A message from before the
  session this device holds is reopened when keys or backup pages arrive.
- **QR verification.** A verified device opens a pairing (3 minutes, one per user, consumed once)
  and shows version 1 ‖ pairing ID (16 B) ‖ one-time secret `s` (32 B) ‖ master fingerprint (32 B),
  base64url, never a public key. The new device checks that the server's master key has that
  fingerprint and posts an ephemeral X-Wing public key. Both screens show six digits,
  HMAC(`s`, Fields(label, pairing ID, new device ID, ephemeral key)): the new device uses its own
  ID, the verified device the one the server names, so the server can neither grind a
  substitute key nor swap in another of the user's devices; on a
  match the verified device sends AES-256-GCM under HKDF(`s`, `kymessages.qr-transfer.v1/inner`) of the
  master and backup seeds, `xwing.Seal`ed to the ephemeral key with info
  `kymessages.qr-transfer.v1`; both layers bind (label, pairing ID, verified device, new device).
  `s` never reaches the server, so the transfer stays confidential even if X-Wing breaks, and the
  X-Wing layer protects against a photographed QR plus recorded server traffic. Both people
  confirm the codes match: the verified device before it sends, the new device before it takes
  the keys. Once approved, adoption (a restore and a new identity too) is one sequence under the
  per-user lock, ending right before the seeds are written: read the backup queue, read the
  identity as published now (its org, master key, version, backup key and generation) and check
  the seeds derive it, so a delayed approval adopts nothing stale and an identity reset meanwhile
  is refused, then check this browser has not taken on a newer identity (or another at the same
  version) in another tab. The very same identity, taken on meanwhile by another attempt, keeps
  its restore and backup progress. When that sequence fails for availability it lets go of the
  lock, waits and runs again whole, a few times, with the consumed transfer held (it cannot be
  consumed again). The screen's close and the pairing's deadline reach the reads and the wait
  for the lock, up to a last check right before the write; a deadline reads as the pairing's
  timeout only before it. The seeds are durable from then on, and announced even when signing
  or listing the device then refuses; when those, or reading the backup in, fail for
  availability, the bounded retry finishes them, never reported as a failed verification.
  Pending retirements run once the enrollment is confirmed: the identity the device holds is
  the one published now, on a list it signed that names this device. Every such authenticated
  list is first observed like any other: a newer one, or another at the same epoch, that leaves
  the device out still moves the high-water mark (or marks the fork), and a rollback or fork
  is the verdict the identity status shows; the enrollment marker stays.
  Pairing lifetimes travel as relative `expires_in_ms`, so a skewed browser clock does not
  expire a live code. Both screens poll for a bounded time, ride out a few failed polls, and stop
  at once on a pairing the server no longer has; the verified device reports the new device
  verified only once it is cross-signed and on the device list, not when the keys are uploaded.
  Closing a screen aborts its requests and waits, the confirmation lookup included (it also ends
  at the deadline): that lookup reads only the user's own entry, and its signal reaches the
  wait for a device still starting (never the start-up itself), the per-user lock and the
  request. The code's lifetime and the new device's wait end a poll request in flight, not only
  the waits between polls; the verified device's screen can be closed while it waits for that
  confirmation without cancelling the keys it already sent, and its cancel removes a pairing
  only while nothing was sealed to it, so a seal whose answer was lost is never undone.
- **Step-up.** Setting up or resetting an identity and deleting the key backup need a sign-in
  from the last 10 minutes. The browser asks for it in place ("Confirm it's you": the password,
  and TOTP when set, for local accounts; a forced KyIdentity sign-in otherwise) and retries;
  signing out to sign in again would delete this browser's keys. A refused TOTP code returns to
  the password step, since it may have spent its challenge, and every attempt gets a fresh
  captcha token (the login spends one): each round starts with none, signing in needs the
  current one, and a challenge that failed can be solved again.
  Signing in again issues a new session
  as the login route always does; the earlier session stays valid until it expires (changing
  that is general session policy, outside E3).
- **Residual (Plan, stated plainly).** Room keys still travel between devices over Olm, which is
  classical: recorded to-device ciphertext (mailbox rows and their backups) is
  harvest-now-decrypt-later exposed until vodozemac ships a PQ Olm (PQXDH PR #120, on hold). Mail
  is deleted on acknowledgement and kept at most 30 days to keep that window short.

## 4. Rooms and messages

- **All rooms are encrypted**, with no per-room switch. Existing rooms become encrypted on
  upgrade.
- **Envelope** (`encoding: "e2ee_room_v1"`, already reserved in `store.MessageEncodingE2EERoomV1`):
  `{"alg":"megolm.v1","sender_key","device_id","session_id","ciphertext"}`. The plaintext inside
  carries `room_id`, `type` (`text`, `edit`, `reply`, `attachment`) and the content, so a
  ciphertext replayed into another room fails to decrypt-check.
- **Key sharing:** before the first message, the sender creates a Megolm session and sends its
  key over Olm to every trusted device of every current member. Messages go out as to-device
  messages, relayed through a server mailbox (`e2ee_to_device`, per recipient device, deleted on
  ack, kept 30 days).
- **Rotation:** a device starts a new Megolm session when a member leaves or is removed, when a
  member's device is removed, after 100 messages, or after 7 days. Joiners get the current
  session from its ratchet index onward only, so they never see history from before they joined.
- **System events** (`system_v1`: joins, leaves, renames) stay server-authored plaintext metadata.
- **Legacy history:** messages stored before the upgrade stay `plain_v1`, are shown with a
  "Sent before encryption" label, and are never re-encrypted. A fresh-database operator
  command, `kymessages purge-plaintext`, deletes them.
- **Edits and deletes:** an edit is a new encrypted message pointing at the original. A delete
  removes the ciphertext server-side, as today.

## 5. Attachments

Format discipline (Plan, E5): a separate random AES-256-GCM key for each file and each
thumbnail; metadata carries `v` and `alg` (`A256GCM`); AAD `kymessages.attachment.v1` ‖ kind
(`file`, `thumb`); the SHA-256 of the ciphertext rides inside the encrypted message. Choose a
chunked (STREAM) format at the start if files can exceed one in-memory AES-GCM call.

The client encrypts each file with AES-256-GCM under a random key before upload. The key, nonce
and SHA-256 of the ciphertext go inside the encrypted message. The server stores and serves only
ciphertext, and quota checks use ciphertext size. Thumbnails are made and encrypted on the
client. Existing attachments stay as they are, under the legacy label.

## 6. Search, notifications and suite features

- **Search:** each client keeps an IndexedDB index of decrypted text, encrypted at rest under a
  non-extractable WebCrypto key. `GET /api/v1/search` and the FTS/`tsvector` index are removed.
- **Push:** the payload says only "New message" and names the room (the room name is already
  server metadata). `push_handlers.go` already strips `e2ee_room_v1` previews.
- **Suite routes are unaffected:** `/api/suite/chat` returns a DM link, presence reads
  KyCalendar/KyPost inputs, and KyCalendar meeting rooms are created server-side with no
  messages. None of them read content.

## 7. Calls

- **Frame encryption everywhere.** LiveKit's E2EE (`ExternalE2EEKeyProvider`, insertable streams
  or `RTCRtpScriptTransform`) encrypts media frames under the call key, for SFU calls and for
  P2P calls. P2P needs it too: DTLS-SRTP fingerprints travel through the server's signaling, so a
  malicious server could otherwise sit in the middle. A browser without encoded-transform
  support cannot join a call; it is told so and offered nothing weaker.
- **Call key:** the first joiner mints it and sends it over Olm to each participant device as
  it joins, using the existing `e2ee_key` signal slot (`internal/chat/protocol.go`). The key
  rotates when a participant leaves.
- **Guests (`/meet/{token}`):** guests are not members and have no Olm identity. A guest's
  browser makes an ephemeral **X-Wing** key pair (never classical X25519; Plan row 22) and sends
  the public key with its knock. The member who admits the guest seals the call key to it with
  `github.com/Busnes-app/ky-primitives/xwing.Seal` (HPKE base mode, KEM **0x647A**,
  HKDF-SHA256, AES-256-GCM; shared `cmd/pqwasm` browser build, Wave 1 #22). Both screens show a 4-word
  code derived from the guest key, so the admitter can compare it with the guest out of band.
  Keys are never put in guest URLs, because the server mints those links
  (`PUT /api/meetings/{id}`).

## 8. Bots

- A bot (`kybot_` token) registers a device and a master key like a user. The owner's client signs
  the bot's master key at creation, and colleagues see "Bot, verified by <owner>".
- The agent skill bundle (`agent-skill/`) ships the vodozemac Python bindings, so OpenClaw/Hermes
  bots decrypt and encrypt locally. A bot's keys live with the bot, never on the server.
- **Incoming webhooks are removed.** Migration disables every existing webhook and writes an
  audit row. `POST /api/v1/webhooks/in/{id}` answers `410 gone` with a pointer to bots. The admin
  UI drops the webhooks pane.

## 9. Server changes

| Area | Change |
|---|---|
| Store | `e2ee_devices` (tenant, user, device_id, identity keys, master-key signature and version), `e2ee_one_time_keys` (claim-once), `e2ee_to_device` mailbox, `e2ee_master_keys` (migration 68: public keys, signatures, recovery wraps, sealed pins, version), `e2ee_key_backup` (sealed sessions per identity version), `e2ee_pairings` |
| API | `POST /api/v1/keys/upload`, `/keys/query` (with `tenant_id` and `master_keys`), `/keys/claim`, `PUT /api/v1/to-device`, `GET` + ack, `GET/PUT /api/v1/keys/master`, `PUT /api/v1/keys/pins`, `POST /api/v1/keys/devices/{id}/signature`, `GET/PUT/DELETE /api/v1/keys/backup`, `/api/v1/keys/pairings` (§9.1) |
| Messages | Accept only `e2ee_room_v1`; `plain_v1` stays allowed for `kybot_` tokens only until E4 (§10) |
| Removed | Server search, incoming webhooks |
| Tenancy | Every key table is tenant-scoped; key queries and claims never cross an org |
| Backups | Capsules carry ciphertext, public keys and the encrypted key backup; restore keeps them |
| Revocation | Removing a device deletes its keys and to-device mail; clients then rotate |

**Signed strings.** Keys and signatures are unpadded base64, as vodozemac writes them. A device
signs, with its Ed25519 key:
- its identity: `kymessages.device.v1\n<user_id>\n<device_id>\n<curve25519>\n<ed25519>`;
- each one-time and fallback key: `kymessages.otk.v1\n<user_id>\n<device_id>\n<key_id>\n<key>`.

The server checks both and refuses anything else in an upload, to reject garbage early. Clients
check again, because they cannot trust the server. A device's identity keys never change:
re-uploading other keys answers `409`. A new mailbox message sends a `to_device` WebSocket event to
the recipient user.

### 9.1 E3 routes

- `GET /api/v1/keys/master` answers `{tenant_id, master}`: null, or `{version, master_key,
  self_signature, backup_key:{public_key, signature}, recovery:{wrapped_master_key,
  wrapped_backup_key}, pins:{counter, sealed}, device_list, backup_generation}`. `PUT` takes `{expected_version,
  master_key, self_signature, backup_key, recovery}`, needs a sign-in from the last 10 minutes
  (the console's step-up, `reauthentication_required`), verifies both hybrid signatures for the
  caller's org and user and version `expected_version + 1`, refuses wraps that are not exactly 93
  (master) and 61 (backup) bytes with version byte 1, and answers `409` unless
  `expected_version` is current (0: none). A first setup replaces a row the user left in another
  org. A replacement (reset) deletes the key backup, pins, pairings, device list and every device
  cross-signature in the same transaction; colleagues then see the identity change. Audited
  `e2ee.master_key_set` / `e2ee.master_key_reset`.
- `POST /api/v1/keys/devices/{id}/signature {version, signature}` stores a verified
  cross-signature on one of the caller's devices (`409` for a stale version). `/keys/query` lists
  only cross-signatures by the current version.
- `PUT /api/v1/keys/pins {version, expected_counter, sealed, signature}`: compare-and-swap, in the
  caller's org, with the master key's `kymessages.pins-write.v1` signature.
- `POST /api/v1/keys/devices/list/reserve {version, expected_epoch, digest, signature}` (the
  master key's `kymessages.device-list-reserve.v1` signature, checked in the reservation's
  transaction; `400` without a valid one) reserves the next
  epoch for the list with that digest (64 lowercase hex) for 30 seconds and answers `{epoch,
  expires_in_ms}`: the same digest keeps its epoch, a different one gets an epoch above every
  one granted before. `409` unless the list is at `expected_epoch` and no other live reservation
  holds it, with `retry_in_ms` while one does. `PUT /api/v1/keys/devices/list {version,
  expected_epoch, epoch, device_ids, signature}` (`device_ids` required, an array; the signature
  over `epoch`): the master-signed device list, compare-and-swap on its epoch and only under a
  live reservation of its digest and epoch (`409` otherwise), which it ends; `/keys/query` lists it with each master key,
  which carries only public fields (never the wraps, pins or backup key).
- `PUT /api/v1/keys/backup {version, generation, sessions:[{room_id, sender_key, session_id,
  first_index, sealed}], signature}` (1–100, `first_index` a uint32; the master key's
  `kymessages.backup-write.v1` signature over the batch for that generation, `409` for another;
  a (room, sender key, session) keeps the copy with the lowest first index; at most 2,000
  sessions and 2 MiB of sealed text per user, checked for every insert and replacement) answers
  `{stored, kept, full, refused}`, `refused` the indexes not stored for the caps;
  `GET ?version=&after_room=&after_sender=&after_session=` pages 200 at a time with the
  generation; `DELETE ?version=` empties it, bumps the generation (answered as `{generation}`)
  and needs a sign-in from the last 10 minutes.
- Pairings: `POST /api/v1/keys/pairings {device_id}` (only a device cross-signed by the current
  key, checked in the same transaction as the insert; one pairing per org and user, enforced by
  a unique index; cancels the user's other pairings) answers `{pairing_id, expires_at,
  expires_in_ms}`; `GET …/{id}` answers
  its state, never the sealed keys; `POST …/{id}/join {device_id, ephemeral_key}` once;
  `PUT …/{id}/sealed {device_id, sealed}` once, from the initiator; `POST …/{id}/consume
  {device_id}` hands the sealed keys to the joined device and deletes the row in one statement;
  `DELETE …/{id}` cancels (`?unsealed=1`, the verified device's: only while nothing was sealed).
  Revoking an account's grants (SCIM deactivation, password or TOTP changes, session
  revocation) deletes its QR pairings too, pending or sealed. Another user's or org's pairing reads as unknown; expired rows are
  unreadable at once and swept every minute; a restore deletes them.
- Every E3 body is decoded by `encoding/json/v2`: member names match case-sensitively, and an
  unknown or repeated name, invalid UTF-8 or trailing data is refused, so no second spelling of
  a signed field can reach a different parser. No body has a field for a private key, recovery key, seed or session
  key (`TestE2EEIdentityBodiesCarryNoSecrets`, `TestE2EEIdentityRoutesRefuseSecretFields`). The two
  recovery wraps are each checked for their own exact length. Identity reads and writes name the
  org in their SQL; tenant purge and erasure remove E3 rows through the `users` cascade.
  Capsules carry `e2ee_master_keys` and `e2ee_key_backup` (the whole database) and restore keeps them.
  A schema test asserts the key backup's key columns collate `C` on PostgreSQL
  (`TestE2EEKeyBackupColumnsCollateC`). Migration 68 is unreleased and amended in place: there is
  no upgrade path for an earlier E3 build's tables, and pre-E3 data is untouched.

The server never receives a private key, a Megolm session key, a call key or a recovery key.
Tests assert this, for example that no request body the server accepts can carry a field
named like a private key.

## 10. Build plan

Every phase leaves every feature working: no phase refuses a message, a bot, a webhook or a
search that the previous phase allowed without shipping its replacement in the same PR. Images
publish only from a published GitHub release (`release-image.yml`), not from a merge to `main`,
so `main` can carry finished phases ahead of the release that switches encryption on.

1. **E1: crypto core and key server** (PR #26). The `web/crypto` Rust crate (vodozemac +
   wasm-bindgen), with its `.wasm` built from pinned source in CI (never committed), the key and
   to-device tables, and the key API with tests, including that one-time keys are claimed
   exactly once across replicas. It changes no existing behaviour.
2. **E2: encrypted rooms.** Megolm send and receive, key sharing and rotation, and the IndexedDB
   store. The web client sends only `e2ee_room_v1`. Bots and webhooks keep working, labelled. In
   the same PR, so nothing is left half-working:
   - **Search moves to the device.** The on-device index replaces `GET /api/v1/search`, which is
     removed; the FTS/`tsvector` index skips `e2ee_room_v1` rows, so it never indexes ciphertext.
   - **Incoming webhooks are removed** (§8): disabled by migration with an audit row,
     `410 gone`, and the pane dropped. Their supported path, bots, still works through E2–E4.
   - **Push previews go.** Notifications say only "New message".
   - **Transition:** the server still accepts `plain_v1`, but only from `kybot_` tokens. The UI
     shows those messages as "Not encrypted (bot)". Every other client is refused `plain_v1`.
3. **E3: identity and recovery** (built post-quantum, §3.1, §9.1). The master key, device
   signing, TOFU warnings, QR verification, the recovery key and key backup. Room keys go only to
   devices the pinned master key signed.
4. **E4: bots as devices.** Bot devices, the Python vodozemac bundle in `agent-skill/`, and the
   owner signing the bot at creation. This PR also makes the server refuse `plain_v1` from
   everyone, bots included, so it ends the E2 transition.
5. **E5: attachments.** Client-side file encryption. **Transition E2–E4:** files uploaded
   before E5 stay plaintext on the server and show a "File not encrypted" label inside the
   encrypted message.
6. **E6: calls.** Frame encryption for P2P and SFU, call key distribution and rotation, and the
   guest admission key with its 4-word code. **Transition until E6:** calls keep today's
   DTLS-SRTP (encrypted in transit, readable by the SFU), and the call screen says so.

**Release gates.**
- **First encryption release:** E1–E5. Encrypted rooms without identity verification (E3) would
  trust whatever devices the server lists, and bots (E4) and files (E5) must not be left
  plaintext. No GitHub release is published from `main` while E2 is merged and E3–E5 are not.
- **Copy for that release:** "messages and files are end-to-end encrypted; calls are not yet."
- **Calls:** E6 ships in a later release. Only then does the copy add calls.

- A hostile review of E1–E5 runs before release, focused on these: whether the server can add a
