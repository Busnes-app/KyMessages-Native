# Web

## Purpose
React 19 + TypeScript + Vite PWA frontend embedding KySecurity color tokens (Busnes light/dark defaults plus `Patina Ky`, `Cyber`, `Nord Dark` (`nord`), `Nord Light` (`paper`), `OLED`), 90-second ephemeral QR device pairing modals, client-side WebCrypto PoW CAPTCHA, and administrative management panels.

## Ownership
Owns user interface components, service worker caching, PWA installation manifests, and frontend theme switching.

## Local Contracts
- A hosted call join's validated `call_ws_path` selects a separate room-affine `ChatSocket`, owned by `HybridCallController`; a socket path must name the joined room. The controller waits for authenticated hello, refreshes its seat after route changes, uses only that socket for signaling/media control, and rejoins through room HTTP after owner reconnection. A signaling-only reconnect retains P2P links when verified call and peer IDs are unchanged, including the designated answerer; a changed call/seat rebuilds media and a refused rejoin closes it. A reconnecting designated offerer resends its own unanswered offer after rejoin; established descriptions remain untouched. Accepted SFU and P2P migrations advance the retained epoch, including P2P notifications that need no media change; older migrations cannot reconnect retired media. Hosted signaling and active roster application wait behind initial setup/recovery on the same bounded transition queue (at most 128 pending signals and one coalesced latest roster); ended current calls still stop media immediately, so early offers are applied only after identity and local media are ready. A session-targeted `peer_signaling_ready` notice resends only the designated offerer’s unanswered offer; outgoing negotiation is serialized per peer. Initial media setup, owner recovery and migrations use one controller-owned transition queue; disposal prevents queued work and rechecks after disconnect. New SFU epochs replace old media credentials. Ordinary chat reconnects do not tear down a separately routed call. Guest call HTTP uses the server's optional `call_room_id`; absent fields keep single-mode paths/behavior. `rtc/hybridCall.test.ts` covers the real socket class with controlled wire events/time, SFU epoch replacement, reconnect and path confinement. Multi-mode bootstrap/reconnect refreshes call rosters through authorized room state routes (four reads in flight, two-second deadline); a global pod snapshot alone is not authoritative. Per-room live revisions fence the entire bootstrap request: an intervening call event, closure, membership removal or local join wins over an older successful or failed owner read. Unchanged rooms still use authoritative results, including null; unavailable rooms retain the latest accessible snapshot. Call-state refs and revisions advance synchronously before React rendering. Room closure/ended-call events stop media and clear the controller from the calling page. Single-mode bootstrap makes no extra requests. This does not establish guest E2EE or a final host-control product model.

- E3 identity (`crypto/identity.ts`, used by `CryptoEngine`; spec §3.1): an unverified device
  trusts and pins no one. `verifiedDevices` gives room keys only to devices whose member's master

  pinned first becomes a pending change. A pending change follows a newer verified key, still
  untrusted. The
  list mark `dlh:<tenant>:<user>:<fingerprint>:<version>` holds the epoch and a member digest and
  only rises (`CryptoStore.update`, one transaction); rollbacks, same-epoch forks and a missing
  list after one was seen trust no device; a list no newer than the mark is checked without a
  write; a fork stays one (`fork` on the mark) until a higher signed epoch. Edits verify the
  predecessor against the local master key, check the `guard` (an enrollment stops once
  `identity:retiring` names this device) right before reserving, reserve the list's digest and

- Encrypted rooms (E2 of `docs/superpowers/specs/2026-11-22-e2ee-design.md`). `crypto/engine.ts` (`CryptoEngine`) is one device: a vodozemac Account in `crypto/store.ts` (IndexedDB `kymessages-crypto-<user>`, pickles under a random 32-byte key wrapped by a non-extractable AES-GCM key; once a device's store opens, `persist.ts` `keepStorage` asks the browser for persistent storage, best effort), self-signed device keys and 50 signed one-time keys plus a fallback key, topped up after a pre-key message; when an upload answers `has_fallback_key: false` (a restore retired it) it publishes a new fallback key. Sending keeps one outbound Megolm session per room, shares its key from the current index as to-device `kymessages.room_key.v1` over Olm to every verified device of every member (signatures checked, device keys pinned on first sight), and rotates after 100 messages, 7 days, or when a member or one of their devices is gone. Receiving binds each room session to the sending device's curve25519 key, user and room; a message must name its room, an edit its message, and each (session, index) belongs to one message ID. Every locked crypto operation checks its cached device ID against the persisted record before work. Identity resets use that same per-user Web Lock and delete only the expected old ID, so concurrent late resets cannot erase a replacement. A `device-reset` message on the existing room-key BroadcastChannel invalidates and aborts matching peer entries (the engine reports its identity before upload, including pending starts); cache checks and a bounded operation retry cover missed notifications and reset/operation timing. Tabs then coalesce startup on the surviving shared identity. `chat/e2ee.ts` wires it to the key API: `client.ts` seals sends and edits and opens fetched and WebSocket messages (in order; opening never waits for a device still starting: the message reads as unavailable and is reopened once it is ready; sealed JSON is capped at 32 KiB so the envelope fits the server's 48 KiB), `parseMessage` keeps an envelope in `envelope`, never `body`, and `e2ee` says `decrypted`, `waiting` (shown "Waiting for this message's key", retried on `onRoomKeys`) or `failed` (with the reason). A failed device start keeps its user in a failed entry and closes its store; a subsequent send or mailbox/member event retries through `startE2EE`, which coalesces concurrent starts, without a socket reconnect. A `to_device` event or a reconnect reads the mailbox. Each mail's sender is checked against the self-signed `sender_keys` the server stored with it (signature and pin, as for listed devices), so room keys from a device that signed out since still arrive. Keys stored before a failed ack or mailbox read are still announced (`onKeys`), before replenishment uploads so a stalled upload cannot delay display. Every key arrival bumps `keyGeneration()` and is broadcast to other tabs (BroadcastChannel `kymessages-room-keys`; tabs share the device's store), and a waiting or retryable message records the generation it was opened at (`e2ee.gen`): `Chat.tsx` reopens such rows from an older generation whenever messages change (device start-up bumps it too), so a key that lands between an open and its display is not missed. A claimed key the crypto core refuses (non-contributory) skips only that device, so one bad device cannot block a room's key. Every send looks up the room's members and devices afresh (no cache: a cached list would miss a member's new device and could outlive a removal), and rotates when a device that had the key is gone; a `room.member` removal also drops the session at once (`roomMemberLeft`). Sign-out deletes the device (`DELETE /api/v1/keys/devices/{id}`, `retireDevice().wait` answers whether it is gone within `RETIRE_MS` (5 s), so a stuck start-up or request never blocks sign-out; a refused logout calls `replaceIfRetired`, which follows the eventual deletion result and replaces only the same still-current device, even when deletion succeeded after the deadline; a sign-out the server refuses after the device was retired starts a new device with `replaceDevice`; both that path and a startup key-upload 404 use `resetDevice`, which removes only the device's own keys (`device`, `account`, `fallback`, `olm:`, `out:`) and keeps received room keys, the replay log, pins and the store wrapping key, so history stays readable; if not, it is recorded as for a revocation) and every crypto store; a revoked session deletes the store and records the device in `localStorage` (`kymessages-e2ee-retire:<user>:<device>`, IDs and flags only) for deletion after its user next signs in here (`abandonDevice`). Inbound sessions and the replay log are keyed by sender curve25519 key and session ID, so a member re-sharing someone's session cannot displace it. `MessageRow` labels `plain_v1` "Sent before encryption" (people), "Not encrypted (bot)", "Not encrypted (guest)" or "Not encrypted (webhook)", and plaintext files (no descriptor names them) "File not encrypted"; an encrypted message not yet opened shows no files. `engine.test.ts` runs engines against `fakeKeyServer.ts`; page tests mock `chat/e2ee` with `chat/e2eeFake.ts`. The crypto store closes every connection on `versionchange` and tells its owner (`onClosed`), which drops the device engine; deletes resolve only on success and reject on error or after 5 s blocked, so `leave()` reports a store it could not delete (`browser/e2ee-store-signout.spec.mjs`). Before wiping, `forgetCryptoStore` records every store's registered device (`storedDevices`, other users of a shared browser included) as pending retirements, so each is removed from the key server at its user's next sign-in. Each device entry owns an AbortController for its key API requests. Stopping it (`stopE2EE`) aborts those requests before closing the store, releasing a per-user Web Lock held by a stalled upload or mailbox read, so the same user can sign in again without reloading. It also cancels start-up, and a cancelled start-up never reopens a store, so revocation (`abandonDevice`) deletes local keys at once. Mail is acknowledged only when handled or itself unreadable: a `Transient` or storage (`DOMException`) failure leaves it queued, and the Olm state a message changed is stored in the same transaction as the room key it carried. A storage error while checking that room key commits nothing, so the mail decrypts again on retry; only a definite refusal stores the spent Olm state. An open that throws is `NOT_YET`, retried like `UNAVAILABLE` (`retryable`).
- Bots as devices (E4). A `bot_` user (`engine.ts` `isBotUser`) has no master key of its own: its devices get room keys, and its room keys are believed, only when on the newest list its owner's pinned master key signed (`kymessages.bot-devices.v1`, `identity.ts` `trustedBot`, with the same keys; the mark only rises like a device list's, so a removal stays removed and a missing list vouches for nothing). Its trust waits on the owner's pin like the owner's devices. The owner's engine lists the bot's uploaded devices with `botDeviceCode` (80 bits of `hash`, the code `kybot.py init` prints) and `vouchForBot` signs exactly the devices whose code was matched; `components/chat/BotDevices.tsx` ("Your bots", chat header on a verified device) does that, and Remove signs a list without the device. A bot's message from a vouched device reads "Bot, verified by its owner" (`crypto/bots.test.ts`, `BotDevices.test.tsx`).
- Encrypted files (E5). `crypto/attachments.ts` is the only format: A256GCM-STREAM v1, a fresh 32-byte key and 7-byte nonce prefix per blob (file and thumbnail separately), 64 KiB chunks, nonce `prefix || index_be32 || final`, AAD `kymessages.attachment.v1 \0 kind index_be32 final`, `kind` `file` or `thumb`; pinned vectors in `attachments.test.ts` are the format, so a change there is a format break. Decryption checks length and SHA-256 of the whole ciphertext before opening any chunk and returns nothing unless every chunk authenticates.
  - Provenance (the contract is `docs/superpowers/specs/2026-11-22-e2ee-design.md` §5). Every message sealed since E5 carries `files` (even empty) and `ref`, its idempotency key. An edit seals only text and `original`: `{kind: 'e5', ref, files: n}` or `{kind: 'legacy', rows}`, never file keys, so a member who joined later gets none. `editProvenance` takes it from the message's own envelope or latest edit, never from the server's kept `original_body`; the editor is unavailable for a legacy `plain_v1` message or reply with uploads, or for a message whose earlier edits name nothing. `needsOriginal`: only an E5 edit with files opens `original_body`, and `expectOriginal` is checked inside `engine.decrypt` before the replay claim, so a substitute never takes an index (`engine.test.ts`, `e2ee.test.ts`). Only uploads from before E5 read "File not encrypted": all rows of an unedited one, only the named `rows` (`plainIds`) of a legacy edit. An E5 message never offers an upload it does not name (a tamper note says it was hidden); a named file the server withheld is "Attachment unavailable". Files whose original is withheld, waiting or refused, or whose older edit names nothing, are unavailable with the reason (and the count when known), shown even with no rows. A waiting original is opened again only once its session's key may have arrived (`keysArrivedFor`; tabs share arrived session IDs).
  - Images. Only still PNG, JPEG and WebP preview (`PREVIEW_MIMES`); GIF and the rest are download-only. Nothing is decoded before `rasterSize(bytes, mime)` finds that type's signature, no animation (APNG `acTL`, animated WebP) and a size within `MAX_DECODE_PIXELS`; a thumbnail must declare exactly its descriptor's size, at most 400 px. The composer shows only the re-encoded thumbnail (`onPreview`), never the picked file. A failed thumbnail only loses the preview.
  - Transfers. `chat/files.ts` uploads only ciphertext (`?encrypted=1`, `encrypted.bin`, `application/octet-stream`), two files at a time; there is no plaintext upload. A download reads into one buffer of exactly `ciphertext_size` (a different `Content-Length` is refused) and ends on a 30 s stall or its deadline (30 s plus 64 KiB/s), which also bounds decryption; a caller leaving is checked on entering the reader, per chunk and before plaintext is returned. `limiter` hands a freed slot straight to the next waiter, drops an aborted waiter at once and passes on a slot handed to one that left. Thumbnails decrypt near the viewport, four at a time; one scrolled away unfinished is cancelled and holds nothing.
  - Lifecycle. Decrypted bytes live only in blob: URLs revoked on unmount (`useSealedUrl`, keyed by the blob and every check applied). A save's controller leaves its button once its URL is revoked (30 s, or a second after leaving). The preview saves the image it decrypted, waiting for it rather than fetching twice. It shows only what the current row offers and closes when that goes. A saved file is always typed `application/octet-stream`, because a typed blob: URL would run as this origin.
  - Reconcile. A deletion always wins: deletion events and fetched tombstones record IDs (`rememberDeleted`, cleared on sign-out), so a delete that arrives before its message, a page or a response still wins. An older edit never replaces a newer one (edits are strictly ordered by the server). History jumps keep unsent copies and their encrypted file descriptors until confirmation or dismissal. Wire messages and events reject IDs beginning with the local send prefix (`pending_`). Room-entry read cursors use synced rows. One confirmation rule on every path (`resolvePending`): an unsent copy is resolved by a synced message in the same room from its sender sealing that send's key as `ref`. A mismatched REST answer marks the send failed. A slim PostgreSQL edit frame fetches its named row from the primary (`fetchMessage`, up to three tries). An invalidation arriving ahead of history drops the stale search entry and waits for the row to load. Staged uploads restored after a reload cannot be sent (their key stayed in the tab that made it) and are offered for removal, except those an unsent message of this tab names. The search index stores decrypted file names, never keys (`Chat.test.tsx`, `MessageRow.test.tsx`, `chat/files.test.ts`, `crypto/attachments.test.ts`).
- `NetworkCheck.tsx` renders on the admin-only Health page: it fetches `/api/admin/network-check`, validates the DTO at the boundary (a malformed or failed response shows `Network check unavailable.`), aborts on unmount and lists five Pass/Warn marks: trusted proxy peer, trusted `X-Forwarded-Proto: https`, https `KY_APP_URL`, host match, and `KY_TRUSTED_PROXIES` naming only single addresses (`trusted_proxies_narrow`). Tested by `NetworkCheck.test.tsx`.
